# 全项目精简优化编码规范

## 命名与边界

- Python 使用 `snake_case`，TypeScript 使用 `camelCase`，类使用 `PascalCase`。
- 主能力使用稳定、唯一的名词；兼容入口以 `compat`、`legacy` 或 `deprecated` 明确标识。
- 不使用 `utils2`、`new_*`、`*_copy` 等并行实现命名；需要迁移时保留一个主实现。

## 路由与 API

- 每个业务能力只允许一个 canonical endpoint；别名必须薄转发，不得复制业务逻辑。
- 同一数据快照的读取、缓存和并发合并集中在服务/仓储层，页面路由不得各自重建。
- 删除路由前先检查前端、脚本、兼容客户端和任务引用；删除后用 404/405 契约验证。
- 响应字段和错误语义保持兼容；必要时加入弃用说明而不是静默改变含义。

## 任务与生命周期

- 每类后台任务只允许一个注册点、一个 owner 和一个停止路径。
- API 启动、健康检查、看门狗和部署脚本不得各自实现一套恢复循环。
- 所有超时使用单调时钟和明确预算；不得用无限等待掩盖重复请求。

## 决策安全边界

- 精简工作不得修改选股公式、评分、排序、阈值、Top N、交易策略或学习样本口径。
- 任何重构必须提供输入/输出不变量或回归快照，证明相同有效输入下决策结果一致。
- 数据缺失只能改善状态表达和重复读取，不能被转换成有效信号。

## 文件与产物

- 先改源码，再由构建脚本生成 `vscode-ext/out/`；禁止手工维护生成文件。
- 临时报告、数据库、日志和发布包不得进入源码模块目录。
- 保留用户未提交改动；不使用大范围格式化掩盖功能差异。

## 验证要求

- 每批至少验证：应用导入、核心健康接口、路由存在性/删除性、实际数据库路径、端口和运行版本。
- 共享缓存必须验证并发合并和 TTL 过期；不能只验证单次 happy path。
- 发布前检查 `git diff`，确认只有本批职责范围内的文件变化。
